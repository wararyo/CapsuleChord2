# CapsuleChord2 電池持ち改善プラン

CapsuleChord2（M5Stack CoreS3 + CapsuleChord2Keypad）の電池持ちを改善するための、
現状分析・測定方法・改善アイデアをまとめる。

- 作成日: 2026-09-11
- 対象: 本体ファームウェア（このリポジトリ）、キーパッドファームウェア（`../CapsuleChord2Keypad`）
- 手持ちの計測器: USBテスター（電流・電圧・積算mAh表示）。Power Profiler / 電流プローブは無し
- 本体は CoreS3 Lite。バッテリーは200mAhで、取り外し可能

### 消費電力の内訳（推定）

実測前の見積もり。優先順位付けの目安として使い、実測で置き換える。

| 消費源 | 推定（電池換算） | 備考 |
|---|---|---|
| ESP32-S3 240MHz 2コア稼働 + PSRAM | 80〜120mA | 無音時のオーディオ処理負荷は実測で約2.7%（5章）。CPU時間の大半はIDLEで、DFS / light sleep が無いのでクロックは下がらない |
| LCDバックライト | 輝度127で30〜50mA、255で60〜80mA | DLDO1経由 |
| LCDパネル・タッチ | 10〜20mA | |
| Grove 5Vブースト → キーパッド | 40〜70mA | RP2040 2コア125MHz（約30mA）+ WS2812待機11mA + ブースト損失 |
| AW88298 / ES7210 / カメラ / IMU 等の待機 | 5〜15mA | 未使用LDOぶん |
| USBスタック | 数mA | バッテリー駆動時は不要 |

合計で概ね200〜300mAとすると、200mAhでは1時間弱という計算になる。実測では、S3（ドラム再生中）で63分40秒だった（5章）。

## 2. 測定方法

### 2.1 基本方針

- USBテスターで **5Vライン（VBUS）** の電流を読む。
- 「電池換算」に直すには次の式を使う。

```
電池電流 [mA] ≈ USB電流 [mA] × k
連続稼働時間 [h] ≈ 200 [mAh] × 0.9 / 電池電流 [mA]     (0.9 は電池の実効容量係数)
```

- `k` は当初、5.0 / 3.8 ≈ 1.3 と見込んでいた（レギュレータの損失はUSB電流に既に含まれているので、効率で割らない）。負荷の給電経路でも異なるはずだった（DCDC降圧の負荷 ≈ 1.3、LDOの負荷 ≈ 1.0、Grove 5V系はUSB給電時に昇圧比がほぼ1になるため電池駆動時より損失が小さく見える）。
- **実測（5章、S3）では `k` ≈ 0.86 で、1を下回った。** 電池の定格容量を使い切った前提での上限値。電力で比べると、USB給電時は約1.12W、電池駆動時は約0.70Wになる。USB給電時にだけ生じる消費がある可能性があるが、原因は未確定。
- そのため当面は、`k` と容量を分けずに、方法Cと方法Aの実測から出した次の経験式で稼働時間を見積もる。

```
連続稼働時間 [h] ≈ 232 / USB電流 [mA]     (232 = 218.5 mA × 1.061 h。S3での実測)
```

- この経験式は、消費の内訳が大きく変わるほど誤差が増える。節目では方法Cで確かめる。
- 例: USBテスターで150mA → 約1.5時間。
- 絶対値より **差分（ある機能をON/OFFしたときの変化）** を重視する。差分は換算誤差の影響を受けにくい。
- USBテスターは瞬時値がふらつくので、**積算mAh機能を使って10分程度の平均**を取る。積算値÷時間で平均電流が出る。
- 安価なUSBテスターでは **5mA未満の差は誤差とみなす**。効果「小」の施策は1つずつ測らず、まとめて導入してまとめて測る。
- AXP2101は電池電流を測れない（M5UnifiedのCoreS3向け `getBatteryCurrent()` は常に0）。電池側の真値は方法C（放電ログ）でしか得られない。
- USBテスターはPCではなくUSB充電器につなぐ（ホストとのUSB列挙を避ける）。

### 2.2 測定を歪める3つの要因と対策

| 要因 | 何が起きるか | 対策 |
|---|---|---|
| 充電電流の混入 | 電池装着中はVBUS電流に充電電流が乗る | 方法A（充電禁止）または方法B（電池取り外し） |
| USB接続でUSBスタックが起動 | 電池駆動時には無いTinyUSBの消費が乗る | **ホームボタンを押しながら電源ON** でUSB初期化をスキップ（既存機能）。または充電専用ケーブル・データ線スイッチ付きテスターを使う |
| 電池なし＋USB給電で5V出力がキャンセルされる | M5Unifiedは「電池なし かつ VBUSあり」だと `setExtOutput(true)` を拒否する。キーパッドが給電されない | 方法Bでは開発ビルドでAW9523レジスタを直接書いてBUS_EN/BOOST_ENを立てる（後述） |

### 2.3 方法A: 電池装着 + 充電禁止（推奨）

実運用に一番近い状態で測れる。キーパッドの5Vも通常どおり出る。

1. 電池を満充電にしておく（充電電流が小さいほど誤差が減る。充電禁止後も電池電圧がVBUSより低いので、電池からの持ち出しはほぼ無い）。
2. 開発ビルド（`CAPSULECHORD_ENABLE_DEV_FEATURES=1`）で、起動直後に充電を禁止する。

```cpp
// setup() の M5.begin() 以降、測定時のみ有効化
#if CAPSULECHORD_ENABLE_DEV_FEATURES
  M5.Power.setBatteryCharge(false);   // AXP2101 対応済み
#endif
```

3. USBテスター経由でPCまたはUSB電源に接続し、**ホームボタンを押しながら電源ON**（USBスタックをスキップ）。
4. 起動後30秒待ってから、積算をリセットし10分計測。
5. 電池電圧が計測中に変わっていないことを `M5.Power.getBatteryVoltage()` のログで確認する（変わっていれば電池から持ち出しており、値を過小評価している）。

### 2.4 方法B: 電池を取り外して測る（予備）

電池なしではAXP2101の動作が実運用と変わり、5V出力のハックも要るため、原則は方法Aを使う。方法Aで充電電流の混入が疑われる場合の予備とする。

充電電流の混入を物理的に排除できる。ただし上記のとおりGrove 5Vが出ないので、対策が必要。

1. 電池コネクタを外す。
2. 開発ビルドで、`M5.begin()` 後にAW9523のポート出力を直接書く（`Power_Class::_core_s3_output` 相当）。

```cpp
// AW9523 (I2C 0x58): P0 bit1 = BUS_EN, P1 bit7 = BOOST_EN
M5.In_I2C.bitOn(0x58, 0x02, 0b00000010, 400000);  // BUS_EN
M5.In_I2C.bitOn(0x58, 0x03, 0b10000000, 400000);  // BOOST_EN
```

3. あとは方法Aと同じ。キーパッドのLEDが点けば給電されている。
4. 注意: 電池なしのNVDC動作では、瞬間的な負荷（スピーカー大音量）でVBUSが落ち込んでリセットすることがある。スピーカー計測は方法Aで行う。

### 2.5 方法C: 電池放電ログ（最終確認用）

改善前後の「実際に何時間持つか」を確認する方法。USBテスターは使わない。

1. 満充電にして、USBを抜き、決めたシナリオ（例: 演奏画面で放置、または自動演奏アプリ）で動かす。
2. 1分ごとに `M5.Power.getBatteryVoltage()` と `M5.Power.getBatteryLevel()` を記録する。記録先はUART（DebugProbe経由でPCに流す）またはLittleFSの追記ファイル。
3. 自動電源OFF（低電圧）までの時間を記録する。
4. 無操作10分の自動シャットダウンが走らないよう、計測時は `InactivityWatcher` を無効化する開発フラグを用意する。

放電曲線から「何%で何分」も分かるので、電池残量表示の校正にも使える。

### 2.6 切り分け（アブレーション）手順

一度に全部変えず、1要素ずつON/OFFして差分を取る。以下を開発メニューまたはビルドフラグで切り替えられるようにすると効率が良い。

| # | 切り替え項目 | 実装方法 | 期待される差分 |
|---|---|---|---|
| 1 | バックライト輝度 255 / 127 / 32 / 0 | `M5.Lcd.setBrightness()` | 最大数十mA |
| 2 | キーパッド切断（物理的に抜く） | ― | RP2040 + WS2812 + ブースト損失 |
| 3 | Grove 5V OFF（キーパッド接続のまま） | `M5.Power.setExtOutput(false)` | #2とほぼ同じになるはず。ブースト自体の待機分が見える |
| 4 | キーパッドLED global 0 | `Keypad.turnOffAllLeds()` | WS2812発光分のみ。待機11mAは残る |
| 5 | オーディオタスク停止 | `stopAudioLoop()` + `i2s_zero_dma_buffer()` | CPU負荷常時分 |
| 6 | AW88298 PWDN | レジスタ0x04 に PWDN=1 | アンプ待機分 |
| 7 | 未使用LDO OFF（ALDO2/3/4） | AXP2101 0x90 のbit1,2,3を落とす | 数mA |
| 8 | CPU 240 → 160 → 80MHz | `esp_pm_configure()` または sdkconfig | 数十mA。音切れが無いか同時確認 |
| 9 | USBスタック無効 | ホーム押し起動 | 数mA |
| 10 | 音を鳴らす（スピーカー / ヘッドフォン） | 自動演奏アプリ | 発音時のピーク |

各行について「ベースライン → 変更 → 戻す」の3点を取り、戻したときにベースラインに戻ることを確認する。

## 3. 改善アイデア

各項目に「効果（推定）」「難易度」「リスク」を付ける。効果は実測で更新する。

### 3.1 ディスプレイ

| アイデア | 効果 | 難易度 | リスク / 備考 |
|---|---|---|---|
| 減光段階でバックライト完全OFF（輝度0でDLDO1が切れる） | 要実測 | 低 | **保留**（使い勝手に影響）。輝度32→0の差分が大きい場合のみ再検討 |
| デフォルト輝度を下げる（現在は設定1=127） | 中 | 低 | ユーザー設定なので既定値変更のみ |
| 減光までの時間を短縮（現在5分） | 中 | 低 | 演奏中は `Inactivity.notify()` されるので消えない |
| 演奏中は自動で暗くする（キー入力で復帰しない「演奏モード」） | 中 | 中 | UX判断が必要 |
| 減光中は `lv_tickframe` の拍アニメーションを止める | 小 | 低 | 描画によるCPU負荷減 |

### 3.2 CPU・ファームウェア（本体）

| アイデア | 効果 | 難易度 | リスク / 備考 |
|---|---|---|---|
| CPUを160MHzに固定 | 中 | 低 | **不採用**。画面更新の遅れ、オーディオ負荷スパイクへの耐性低下が懸念されるため、DFSで対応する |
| DFS有効化（`CONFIG_PM_ENABLE`、min 80 / max 240MHz） | 中〜大 | 中 | ESP-IDFのDFSは負荷追従ではなくロック方式。ロックが無いと常に最低周波数になるので、オーディオ処理中とLVGL描画中は `ESP_PM_CPU_FREQ_MAX` ロックを取る。I2Sが必要とするAPBロックも確認。無音時休止（3.3参照）と組み合わせる |
| 自動light sleep（`CONFIG_FREERTOS_USE_TICKLESS_IDLE`） | 大（無音時） | 高 | I2S常時稼働中は入れない。BLE・USB・I2Cタスクの周期も見直しが必要 |

| `cfg.internal_imu = false`、`cfg.internal_mic = false` | 小 | 低 | IMU・マイクは本機では未使用 |

### 3.7 ハードウェア・運用

## 4. 優先順位とロードマップ

### 目標シナリオ

- 主指標: **S3 演奏中（内蔵音源・スピーカー）の連続稼働時間**（方法Cで測る）
- 副指標: S1 アイドル
- 無操作の放置中にしか効かない施策は優先度を下げる。

### フェーズ0a: 粗い内訳とベースライン（まずここから）

1. 開発フラグを追加する: `setBatteryCharge(false)`、`InactivityWatcher` 無効化、減光状態の強制、電池電圧・残量の1分ごとのログ。（実装済み）
   - 開発ビルド（`CAPSULECHORD_ENABLE_POWER_LAB`）のメニュー「システム」に「[測定] 充電禁止」「[測定] 無操作タイマー無効」「[測定] 減光を強制」がある。保存されず、再起動で解除される。
   - 電力ログは `src/PowerLab.cpp`。起動時と以降1分ごとに `PWRLOG,` で始まるCSV行をUARTへ出す（`esp_rom_printf` なので、通常起動でUSB CDCにログが移っていてもDebugProbe側で読める）。列は `uptime_s,vbat_mV,level_pct,vbus_mV,charging,charge_disabled,audio_avg_us,audio_max_us,audio_load_pct`。`audio_load_pct` は1バッファ周期（128サンプル / 48kHz = 2666µs）に対するオーディオ処理時間の平均割合。
2. 方法AでS1・S3を測る。あわせて、キーパッドを抜く、輝度 255 / 127 / 32 / 0、ホーム押し起動と通常起動、の差分を取る。（S1・S3のベースラインは済み。差分測定は未実施）
3. 方法CでS3を1回フル放電し、ベースラインの稼働時間と換算係数 `k` を決める。`k` を出すには、方法Cと同じシナリオを方法Aでも測る必要がある。（済み: 63分40秒、`k` ≈ 0.86）
4. `audioProcessTime` からオーディオタスクのCPU使用率を記録する（無音時休止・DFSの効果見積もりに使う）。（無音時は済み: 約2.7%）

### フェーズ0b: 詳細切り分け（必要な場合のみ）

- 0aで「キーパッド・バックライト以外」が大きい場合に、CPU・オーディオ・LDOなどの切り替えを電力実験メニューにして、2.6の切り分けを行う。

### フェーズ1: 低リスク（使い勝手に影響しないもの）

- キーパッド: RP2040クロック 125→48MHz、core0 WFE化、WS2812データを変更時のみ送出（実装済み。キーパッドFW 3.2、`feature/power-saving`。S1で約−11 mA（USB側）。5章）
- 次の小効果の施策はまとめて導入し、まとめて測る:
  - IMU/マイク初期化スキップ（以前から実装済み: `main.cpp` の `m5cfg.internal_imu/internal_mic = false`）
  - 電池駆動時のUSB無効化（実装済み）: I2Cスレッドが1秒ごとにVBUSを見て、USB給電を検出した時点で `loop()` からUSBを開始する。ホーム押し起動では従来どおり開始しない。効果は方法Aの「ホーム押し起動 / 通常起動」の差分で見積もれる（瞬時値で約2.5 mA。5章）
  - ヘッドフォン時のAW88298停止（実装済み）: M5Unifiedのスピーカー無効化と同じく、I2SEN=0 にしてAW9523 P0_2（AW_RST）をLowにする。スピーカー復帰時はAW_RSTをHighにして再設定する。従来コードはAW_RSTの操作先アドレスを誤ってAW88298（0x36）にしていたので、AW9523（0x58）に修正。効果はS4（ヘッドフォン）で測る
  - 未使用LDO OFF（実装済み）: `setup()` の `M5.begin()` 直後に、CoreS3 なら ALDO3 / ALDO4 / BLDO1 / BLDO2 をOFFにする（約−7 mA。5章）。
    - レールの用途に資料間の食い違いがあり、電源の落ちたデバイスがバスを引きずるおそれもあったので、開発メニューの切り替えで1本ずつ確かめてから組み込んだ（確認後、メニュー項目は削除）。
    - ALDO2 は電流に効かず、OFFにすると画面が少し暗くなり、ヘッドフォンを抜いた後にスピーカーが鳴らなくなるので対象外

### フェーズ2: 構造変更

- DFS（min 80 / max 240MHz、オーディオ処理・LVGL描画中は `ESP_PM_CPU_FREQ_MAX` ロック）。160MHz固定は採用しない
- 無音時のオーディオタスク休止（DFSの効果を引き出す前提条件）
- 無操作時のキーパッドスキャン間引き（最初のキー入力の遅延が許容範囲か確認）

### フェーズ3: ソフトウェアの発展

- light sleep の検討
- タッチのINT駆動、キーパッド→本体のINT通知（既存の配線で済む範囲）
- RP2040の dormant / sleep モード

### フェーズ4: ハードウェア

- WS2812の電源をMOSFETで切る基板改修
- INT線など配線の追加が必要なもの

### 保留（使い勝手に影響するもの）

0aの実測で効果が大きいと分かった場合のみ再検討する。

- 減光段階でバックライトOFF（輝度32→0の差分で判断）
- 減光段階でキーパッドLED完全OFF（WS2812の待機分が残るので、削れるのは点灯分の約5mAだけ。5章）
- 減光中のGrove 5V OFF（キーパッドが再起動し、キー入力で復帰できない）
- 減光・電源OFFまでの時間短縮（既定値は変えず、設定項目にするなら可）

### 判断基準

- フェーズ1で目標に届けばフェーズ2以降は保留する。目標値は0aの測定後に決める（例: S3の稼働時間を1.5倍）。
- 音切れ・入力遅延・復帰の不自然さが出る変更は、効果が大きくても採用しない。
