# CapsuleChord2 Firmware Roadmap Memo

作成日: 2026-05-29

このメモは、CapsuleChord2 の「まずは10台販売」を見据えたファームウェア改善方針の会話メモです。
実装計画というより、優先順位と判断基準を残すためのロードマップです。

## 背景

CapsuleChord2 は、すでにコード演奏・内蔵音源・USB MIDI・BLE MIDI・複数アプリ・設定保存などの主要機能を備えている。
一方で、販売台数を増やす前には「楽器として普通に触っていて安心できること」「ユーザーが迷わず設定できること」「不具合調査・サポートに必要な情報が本体から取れること」が重要になる。

そのため、当面は派手な新機能だけでなく、安定化・診断・基本操作性を優先する。

## 基本方針

1. **まずは10台販売に耐える信頼性を作る**
   - 普通に触っていてクラッシュしないこと。
   - 音が鳴りっぱなしにならないこと。
   - 出力切替・電源・設定保存などが安全に動くこと。

2. **メニューとホーム画面の役割を分ける**
   - メニュー画面: 製品設定・診断・リセットなど。
   - ホーム画面: 演奏中にすぐ触りたい調・テンポ・出力先など。

3. **診断機能を先に整え、クラッシュ修正の足場にする**
   - 「ファームウェア情報画面」は単なる About ではなく、販売後サポートやクラッシュ調査に使える診断画面として作る。

4. **展示会で映える機能は、通常利用を壊さない形で追加する**
   - デモモードや展示用ショートカットは明示的に分ける。
   - 通常ユーザーが意図せず発動する隠し挙動を減らす。

## 優先ロードマップ

### Phase 1: 診断と安定性

最優先。10台販売前に、通常利用で不安になる要素を減らす。

- 不意なクラッシュの調査・修正
  - 普通に触っていてたまにクラッシュする症状があるため最優先。
  - まずは原因追跡に必要な情報を本体上で確認できるようにする。
- ファームウェア情報 / 診断画面
  - reset reason
  - firmware version
  - git commit hash / build date
  - build environment
  - LittleFS mount 状態
  - 音色データ検出状況
  - 現在の出力先
  - 現在の音色ID
  - キーパッド protocol: Legacy / V3
  - キーパッド FW version
  - battery state
  - USB MIDI 有効状態
- ノート停止漏れの点検
  - アプリ停止時、出力切替時、電源OFF要求時に NoteOff が漏れないか確認する。
- 出力切替の安全性
  - Internal / BLE MIDI / USB MIDI の切替時に、古い出力先へ鳴りっぱなしが残らないようにする。
- 無操作 dim / power off の安全性
  - LED消灯、設定保存、音停止、電源OFF要求の順序を確認する。

### Phase 2: 製品としての基本設定

現状では設定項目が少なすぎるため、メニュー画面を製品設定の中心として拡充する。

優先度が高い設定:

- 出力先設定
- 音色設定
- スピーカー音量
- ヘッドホン音量
- 画面明るさ
- キーパッドLED明るさ
- ファームウェア情報 / 診断画面
- 設定リセット

優先度が低め、または後回し候補:

- ネットワーク設定
- 言語切り替え
- ライセンス情報

※ 実体がまだ薄い項目は、空のメニューとして増やすより、必要になってから作る。

### Phase 3: 演奏中の操作性

メニュー画面へ行かなくても、演奏中に頻繁に変える項目へすぐアクセスできるようにする。

- ホーム画面から調を簡単に変更する
  - 既存の Back/Menu で半音ずつ変える操作を置き換える想定。
  - スケール表示タップ、または専用ダイアログなどを検討。
- ホーム画面からテンポを簡単に変更する
  - 既存の `TempoDialog` をより直接開ける導線を作る。
- ホーム画面から出力先を簡単に変更する
  - Internal / BLE MIDI / USB MIDI を演奏前後にすぐ切り替えられるようにする。
- メニューボタン単押しでメニューを開く
  - 調変更の導線を別に用意できた後、Back/Menu で調を変える役割を外す。
  - 物理ボタンの役割をより直感的にする。

想定される物理ボタン整理:

- Back: 戻る / 閉じる
- Home: ホーム / アプリ一覧
- Menu: メニュー表示

### Phase 4: 展示・魅せ機能

安定性と基本操作が整った後、展示会で映える機能を追加していく。

候補:

- デモモード
- 自動演奏の見せ方改善
- LED演出
- シーケンサー / ベース / ドラム連携強化
- 展示用プリセット
- デモ曲追加

注意点:

- 通常モードと展示用モードを混ぜすぎない。
- 長押しショートカットなどは、通常ユーザーが偶然発動しても困らない設計にする。
- 既存の Home 長押し展示用ショートカットは、将来的には明示的なデモモードへ移すことを検討する。

## 最初の着手候補: ファームウェア情報 / 診断画面

最初に作るなら、ファームウェア情報画面が良い。

理由:

1. 10台販売前のサポート性が上がる。
2. 不意なクラッシュ修正の足場になる。
3. メニュー画面拡充の一部として自然に入れられる。
4. 既存の演奏ロジックを壊しにくい。

### 実装方針案

単なる UI 直書きではなく、情報取得層を作る。

例:

```text
SystemInfo / FirmwareInfo
  - firmwareVersion
  - buildDate
  - gitCommit
  - buildEnvironment
  - resetReason
  - littleFsMounted
  - timbreCount
  - keypadProtocol
  - keypadVersion
  - outputType
  - timbreId
  - usbMidiEnabled
```

UI はこの情報を表示するだけにする。

これにより、後から以下へ流用しやすくなる。

- ファームウェア情報画面
- 起動ログ
- クラッシュ調査
- シリアル出力
- 将来的な診断エクスポート

### 最小MVP

まずは以下だけでも価値がある。

- firmware version / build date
- git commit hash
- reset reason
- LittleFS mount 状態
- Keypad protocol / FW version
- current output target
- current timbre id

## 今すぐ大規模リファクタしない方がよさそうな領域

販売前後ではリスクが高いため、明確な不具合や必要性が出るまでは大きく触りすぎない。

- `main.cpp` の全面分割
- `AppManager` の全面設計変更
- `ChordPipeline` の全面設計変更
- `SettingsStore` の全面作り直し
- UI フレームワークの大規模変更

必要になった箇所だけ、小さく安全に改善する。

## 判断基準

迷ったときは、以下の順で優先する。

1. 10台販売時にユーザーや開発者が困る不具合を減らすか
2. クラッシュ調査・サポートが楽になるか
3. 演奏中の操作が直感的になるか
4. 展示会で魅力が伝わるか
5. 将来の実装が少し楽になるだけではないか

「将来きれいにしたい」だけの変更は、販売前は後回しにする。
